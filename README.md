# WSTT

WSTT — Android-приложение для работы с туннельным VPN-подключением. Проект включает Android-клиент и компоненты на Rust.

## Возможности

- Подключение и отключение туннеля.
- Управление параметрами подключения.
- Настройка маршрутизации приложений через списки исключений.
- Просмотр журнала событий и диагностика соединения.
- Управление подключением через плитку быстрых настроек и виджет.
- Новые ссылки WSTT используют отдельную схему `wst://`, не конфликтующую с `csqtt://` приложения CSQTT.

## Требования для сборки

- Android Studio или Android SDK Command-line Tools.
- JDK 17.
- Android SDK Platform 37.0.
- Android Build Tools 37.0.0.
- Rust toolchain — для сборки и изменения нативных компонентов проекта.

В проекте используется Gradle Wrapper, поэтому отдельная установка Gradle не требуется.

## Сборка Android-приложения

Клонируйте репозиторий:

```bash
git clone https://github.com/Ghalgha/Winston-Smith-Tunnel.git
cd Winston-Smith-Tunnel
```

Перед сборкой APK сгенерируйте нативные компоненты клиента и серверные бинарные файлы (включая веб-панель):

```bash
scripts/build_android_native.sh
rust-server/build_linux.sh --no-tests
```

Соберите отладочную версию:

**Linux / macOS**
```bash
chmod +x gradlew
./gradlew :app:assembleDebug
```

**Windows**
```powershell
.\\gradlew.bat :app:assembleDebug
```

Готовый APK будет находиться в каталоге:

```
app/build/outputs/apk/debug/
```

Для сборки нужны установленные Android SDK Platform 37.0 и Build Tools 37.0.0. Если Gradle в вашей среде ожидает каталог `platforms/android-37`, а SDK установлен в `platforms/android-37.0`, настройте совместимый путь к каталогу платформы.

## Подпись релизной версии

Для локальной сборки релиза необходимо отдельно настроить ключ подписи. Используются следующие параметры:

- `KEYSTORE_FILE` — путь к файлу хранилища ключей;
- `KEYSTORE_PASSWORD` — пароль хранилища;
- `KEY_ALIAS` — имя ключа;
- `KEY_PASSWORD` — пароль ключа.

Их можно передать через Gradle properties, переменные окружения или локальный файл `local.properties`. Не добавляйте этот файл, keystore и пароли в Git. Не используйте отладочный ключ для публикации релизов.

## GitHub Actions

Проверочная сборка Android CI создаёт только временный debug-артефакт и не публикует его как релиз. Для публикации подписанного релиза запустите вручную workflow **WSTT release** после добавления GitHub Actions secrets `KEYSTORE_BASE64` (содержимое постоянного keystore в Base64), `KEYSTORE_PASSWORD`, `KEY_ALIAS` и `KEY_PASSWORD`. Используйте один и тот же keystore для всех обновлений.


## Совместная установка с оригинальным CSQTT

WSTT использует отдельные системные ресурсы и может работать на том же VPS, что и оригинальный CSQTT:

- UDP-порт сервера: `46100`; HTTPS-панель: `46102`; внутренние диагностические сокеты: `127.0.0.1:46103` и `127.0.0.1:46104`.
- TUN-интерфейс: `wstt1`; IPv4-подсеть: `10.67.68.0/24`; IPv6-подсеть: `fd67:68::/64`.
- Локальный SOCKS5 по умолчанию: порт `45100` (вместо CSQTT `45000`).
- TPROXY: mark `0x7532`, таблица и priority `30002`; отдельные комментарии firewall с префиксом `WSTT_`.
- systemd-служба `wstt.service`; конфигурация и база данных в `/etc/wstt`; Docker-контейнер `wstt`.
- Certbot state WSTT хранится отдельно в `/etc/wstt/letsencrypt`, `/var/lib/wstt/letsencrypt` и `/var/log/wstt/letsencrypt`; каталог `/etc/letsencrypt` оригинального CSQTT не изменяется.

HTTP-01 challenge обеих систем использует TCP/80. WSTT сериализует собственную выдачу и продление сертификатов и проверяет занятость порта; если TCP/80 уже занят, выпуск откладывается с self-signed fallback. При одновременном старте Certbot в WSTT и CSQTT гонка остаётся, пока CSQTT не использует ту же блокировку.

Установщик и удаление WSTT ограничены этими именами и правилами. Они не останавливают службу CSQTT, не удаляют `/etc/csqtt`, бинарники CSQTT или его firewall/TPROXY-правила. Установки WSTT старых версий, которые использовали общие идентификаторы (`csqtt.service`, `csqtt1`, `/etc/csqtt`, `CSQTT_TPROXY`), автоматически не мигрируются: эти ресурсы могут принадлежать оригинальному CSQTT. Их перенос или удаление допустимы только после проверки владельца каждого ресурса.
